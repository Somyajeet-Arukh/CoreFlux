# Optional experimental performance-counter infrastructure

This document describes the original counter-based study. The main telemetry study is [module telemetry scalability and runtime characterization](telemetry-scalability.md). Hardware performance counters, IPC, cache/branch metrics, and microarchitectural analysis are **not** CoreFlux completion requirements. The tools and previous WSL2 observations below remain available for optional experimentation; their hardware-dependent conclusions are unvalidated on this host.

`coreflux-workload` now supports CPU arithmetic, sequential memory scanning, randomized pointer chasing, frequent yielding, CPU/sleep mixed activity, high-frequency sleep/yield telemetry stress, and periodic wake-up latency. The latency mode reports p50/p95/p99 wake delay in microseconds; the other modes report operations and a checksum. Operation units differ by mode, so compare a mode only with repeated runs of that same mode.

Run the suite inside the development container with `--privileged`:

```sh
cmake -S . -B build && cmake --build build -j4
python3 scripts/run-performance-suite.py
python3 scripts/analyze-performance.py
```

The runner pins workload threads to one allowed CPU, calls Linux `perf stat`, and writes `benchmarks/reports/performance-suite.json`. It uses two threads except for the single-thread latency mode. By default it performs three two-second trials per mode and reports medians, with each trial preserved. Use `--seconds` and `--repeats` to change this. Each memory worker has a configurable 32 MiB data array (`--memory-mib`); two workers exceed this WSL host's 30 MiB last-level cache. Select a size above the target native host's cache capacity when validating cache behavior.

Memory arrays and random pointer chains are prepared before the measured window. The workload signals `READY`, the runner enables perf counters, then starts timed work; after `DONE`, it disables counters before output and cleanup. This uses [perf stat's documented control and delayed-start interface](https://man7.org/linux/man-pages/man1/perf-stat.1.html). The measured memory task-clock is about two seconds and has only a handful of page faults, confirming preparation is excluded. Every counter has an availability status; available counters also carry the measured value, unit, running percentage, and multiplexing flag. A median counter is omitted if any contributing trial was unavailable or multiplexed. IPC is computed only when cycles and instructions are both available and unmultiplexed.

`analyze-performance.py` turns the raw suite into `benchmarks/reports/performance-correlation.json`. It derives trial-level IPC, cache and branch misses per million instructions, context switches per second, and task-clock per second, then reports medians. It compares sequential and random memory, and CPU and context-switch modes. A null comparison means at least one required measurement was unavailable, multiplexed, or had a zero denominator; no hardware value is invented. Its `hardware_validation_status` is `ready_for_interpretation` only when IPC is present for the four core comparison modes and cache-miss rates are present for both memory modes. That status is a data-availability gate, not proof of a causal relationship.

The latency-sensitive mixed-contention fixture is `scripts/benchmark-latency-contention.py`. It runs paired periodic-wake trials alone and with a CPU-bound noisy neighbor pinned to the same CPU; order alternates by pair. It saves `benchmarks/reports/latency-contention.json`. On this WSL host, five paired trials produced median p99 delays of 350 µs alone and 118 µs with the neighbor. The direction is counterintuitive and may reflect WSL/virtualized scheduling and idle behavior. The experiment establishes a repeatable fixture, not a claim that contention improves latency. The affinity-isolation experiment remains in `scripts/benchmark-policy.py`.

Pass `--with-ebpf` to capture scheduler events in the same trial. The container needs `--privileged --pid=host`, and tracefs must be mounted. The saved event count covers the pinned CPU during the workload's start/end interval, not only the workload process; Docker's PID namespace prevents a reliable per-process match on this host. The report also records the eBPF reader's dropped-event count. A two-pair telemetry run observed medians of 4,067 and 4,014 CPU-wide scheduler events for baseline and contention, respectively, with zero reader drops. These counts do not explain the lower wake delay under contention. The eBPF reader itself processes many host-wide events and may perturb the experiment.

On the current WSL2 kernel, cycles, instructions, cache misses, and branch misses are unsupported, so IPC and a hardware-counter correlation cannot be established here. Software counters do work. Across the refreshed three two-second trials, median context switches were 2,123,309 for the context-switch workload, 2,015 for the latency workload, and 517 for the CPU workload. These measurements confirm distinct OS-level behavior, but they are diagnostic observations on one WSL host. On a native Linux host with an exposed hardware PMU, rerun the suite and check counter availability and `running_percent` before comparing hardware values. Control background load before drawing performance conclusions.

The current correlation report therefore says `awaiting_supported_unmultiplexed_counters`. Its OS-side comparison finds a roughly 4,107× context-switch rate for the context-switch mode relative to CPU mode, while IPC and cache-miss comparisons remain null. The report records 30 exact hardware-counter gaps across the repeated trials. The host metadata records its Intel i7-14650HX, 30 MiB last-level cache and perf version. The WSL guest exposes no CPU PMU device or `arch_perfmon` CPU feature. [Microsoft's WSL issue](https://github.com/microsoft/WSL/issues/12836) reports this limitation on newer Intel generations; setting `.wslconfig` alone is not a demonstrated fix for this machine.

To complete this optional hardware-counter study on a Linux host with usable counters, run the suite, then use `python3 scripts/analyze-performance.py --require-hardware`. The analyzer writes the full report and exits with code 3 while required counters are unsupported, multiplexed, or the memory footprint does not exceed the last-level cache. Only after it passes should the measured IPC/cache differences be interpreted alongside OS rates. Do not infer cache behavior from the page-fault counts.
